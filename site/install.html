Setting up the server

  1. 01

    Make a Google sign-in client

    Sign-in is Google's, so there is no password for this server to store or lose. In the Google Cloud console, create an OAuth client of type Web application. Add https://your-address/auth/callback as an authorised redirect URI. Keep the client id and secret.

  2. 02

    Put the binary where it will live

    One executable and one SQLite file beside it. It serves the browser, the phone apps and the watch from the same process, so there is nothing else to install — no database server, no reverse proxy required, no runtime.

  3. 03

    Write the settings file

    A file called .env next to the binary. The minimum is a database path, a Google client, and who may sign in.

  4. 04

    Start it

    It listens on port 8080 and prints the address a phone on the same network can reach it at. If the database path is wrong it refuses to start rather than quietly serving an empty list.

  5. 05

    Open it and sign in

    Visit the address in a browser and sign in with Google. That is the whole setup — you now have a list.

The settings file

# The Google client from step 01.
GOOGLE_CLIENT_ID="000000000000-xxxxxxxx.apps.googleusercontent.com"
GOOGLE_CLIENT_SECRET="GOCSPX-xxxxxxxxxxxxxxxxxxxxxxx"

# An absolute path, and mind the three slashes.
DATABASE_URL="sqlite:///var/lib/shopping-list/data.db"

# The address this is served from. Changes that claim to come from
# anywhere else are refused.
PUBLIC_ORIGIN="https://lists.example.com"

# Who may sign in. Comma-separated, or "*" to admit anyone.
ALLOWED_EMAILS="you@example.com,someone@example.com"

Starting it

./shopping-list-server

  INFO listening on 0.0.0.0:8080
  INFO reachable from this network at http://192.168.1.24:8080
  INFO sign-in restricted admitted=2

Every setting

NameNeededWhat it is
DATABASE_URLrequired Absolute path to the SQLite file, as sqlite:///…. The server will not create a missing database — a wrong path fails loudly instead of serving an empty one.
ALLOWED_EMAILSrequired The addresses allowed to sign in, comma-separated, or * to admit anybody. There is no default: leaving it out looks exactly like meaning “anyone”, so the server refuses to start instead.
GOOGLE_CLIENT_IDrequired The web client from step 01.
GOOGLE_CLIENT_SECRETrequired Its secret. Used for the browser sign-in flow only.
PUBLIC_ORIGINrecommended The address this server is served from. Defaults to http://localhost:8080. Share links are built from it, and state-changing requests that say they came from elsewhere are refused.
REDIRECT_URIoptional Where Google sends the browser back to. Defaults to http://localhost:8080/auth/callback; set it to match your own address.
SESSION_INSECUREoptional Set to true only for a local run over plain http://. Anything reachable from outside must not have it — the session cookie is marked Secure unless this says otherwise.
GOOGLE_IOS_CLIENT_IDoptional The iPhone app's own client id, if you build the iOS app yourself. One provider issues a different client id per platform, so the phone's tokens carry a different audience from the browser's.
GOOGLE_ANDROID_CLIENT_IDoptional Normally nothing. Android is given the web client id above and its tokens come back addressed to that. Set this only if one turns up addressed elsewhere.
RUST_LOGoptional How much the server says. Defaults to something readable.

Connecting an app

Install the app, open it, and it asks for the server address before anything else — something like https://lists.example.com. Enter it, sign in with Google, and you are on the list.

The address is kept in the app's settings and can be changed later under Settings → Server. Changing it signs you out and clears the lists held on the device, because those belong to the old server.

Things that catch people out

  • localhost on a phone means the phone. Use the address the server prints at startup, and make sure the phone is on the same network.
  • Android refuses plain http://. A server reachable from outside your home should be served over https:// anyway.
  • “This account may not use this server” means sign-in worked and the address is not admitted. Add it to the server's list and try again.
  • The watch is set up by the phone. Open the app on the paired iPhone once; the watch takes the address and the sign-in from there.

Putting it on the internet

Everything above works on a home network as it stands. Reaching it from outside means a name, a certificate and a way in — a reverse proxy in front of port 8080 is the usual answer. The server does not serve HTTPS itself.

Do that before you hand the address to anybody: the token in every request is a bearer credential, and on plain HTTP it travels in the clear.
