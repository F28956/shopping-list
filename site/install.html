Do you need a server?

Probably not to start with. Install the app and it works immediately — it keeps its own list on the device, and it is not a cut-down version of the real thing: the app carries the server's own code and runs it locally, so the typed lines are parsed the same way, the categories are the same categories, and the history is the same history. There is nothing to sign in to and nothing to configure.

Run a server when you want one of these:

  • The same list on more than one device. Your phone and your laptop, or your phone and somebody else's.
  • Sharing a list. Invitations need somewhere to meet.
  • The web app. The browser has no device to keep a list on.

You can decide later. Adopting a server takes what is already on the device with it — lists, items, categories and history — so nothing is lost by starting without one. If somebody else runs a server and has invited you, skip to connecting an app.

Setting up the server

  1. 01

    Decide how people sign in

    There is no password for this server to store or lose; it verifies tokens Apple and Google have already issued. Apple needs no console at all — a native token's audience is the app's bundle identifier, which is the same for every install, so you list it in APPLE_BUNDLE_IDS and that is the whole of it. Google is how the browser and Android sign in, and it needs an OAuth client of type Web application from the Google Cloud console, with https://your-address/auth/callback as an authorised redirect URI. Keep the client id and secret.

  2. 02

    Put the binary where it will live

    One executable and one SQLite file beside it. It serves the browser, the phone apps and the watch from the same process, and it can hold its own certificate — so there is nothing else to install: no database server, no runtime, and a reverse proxy only if you already wanted one.

  3. 03

    Write the settings file

    A file called .env next to the binary. The minimum is a database path and a Google client. Who may sign in is managed from inside the app once you have claimed it. Running it as a service instead? The same keys go in /etc/shopping-list/server.env — see running it as a service.

  4. 04

    Give it a certificate

    Released apps refuse plain http://, so this is a prerequisite and not a finishing touch. Either let the server order one itself with TLS_MODE=acme, or point it at PEM files you already have with TLS_MODE=files. Leave it off only behind a proxy that terminates TLS for it. See HTTPS.

  5. 05

    Start it and claim it

    It prints the address a phone on the same network can reach it at, and — while nobody owns it yet — a claim code. Sign in with that code and the server is yours. The code is new on every restart and is never stored, so a port that was briefly public does not cost you the box.

The settings file

# An absolute path, and mind the three slashes.
DATABASE_URL="sqlite:///var/lib/shopping-list/data.db"

# The address this is served from. Changes that claim to come from
# anywhere else are refused, and share links are built from it.
PUBLIC_ORIGIN="https://lists.example.com"

# The browser and Android sign in with Google.
GOOGLE_CLIENT_ID="000000000000-xxxxxxxx.apps.googleusercontent.com"
GOOGLE_CLIENT_SECRET="GOCSPX-xxxxxxxxxxxxxxxxxxxxxxx"
REDIRECT_URI="https://lists.example.com/auth/callback"

# The Apple apps sign in with Apple. No console, no client id --
# just the bundle identifier the app ships with.
APPLE_BUNDLE_IDS="dev.f28956.shopping-list"

# A certificate this process orders and renews by itself.
TLS_MODE="acme"
TLS_DOMAINS="lists.example.com"
ACME_CONTACT="you@example.com"

HTTPS

The server terminates TLS itself. That is worth saying plainly because it used not to: there is no longer a reverse proxy in the minimum setup, and TLS_MODE chooses between three arrangements.

TLS_MODE What it does
acme Use it when you have a name pointing at the box. It orders a certificate from Let’s Encrypt and renews it in-process — no cron, no restart, connections in flight undisturbed. Needs TLS_DOMAINS, a name that resolves, and the challenge to reach it: the CA connects to public 443 or 80 and there is nowhere to tell it otherwise. Serving on PORT=443, or forwarding public 443 to whatever port you serve on, both work — the challenge arrives on the same socket as ordinary traffic. Behind CGNAT with nothing forwarded, use files.
files Use it when you already have a certificate. Reads a PEM chain and key from TLS_CERT and TLS_KEY — a corporate CA, a wildcard, or mkcert on a development machine. Give it the whole chain: a leaf on its own works in a browser that cached the intermediate and fails on a phone that did not.
off Use it when something in front already does TLS. The default, and cleartext. Correct behind Caddy or nginx, and a leak anywhere else — it says so in the log every time it starts.

Under acme the certificate and account key are kept in TLS_CACHE_DIR rather than in the database, and the directory must be 0700. The database is the thing that gets copied to a laptop to debug and attached to an issue; losing the cache costs a fresh order, and leaking the database should not also cost a private key.

Leave ACME_DIRECTORY alone unless you are fighting with port forwarding. Staging produces a server that starts cleanly, serves happily, and is rejected by every client — a failure that looks like a success everywhere except a browser’s advanced-options dialog.

Every setting

Name Needed What it is
DATABASE_URL required Absolute path to the SQLite file, as sqlite:///…. The server will not create a missing database — a wrong path fails loudly instead of serving an empty one.
GOOGLE_CLIENT_ID required The web client from step 01. Required because it is how the browser signs in, and a server nobody can reach in a browser cannot be administered.
GOOGLE_CLIENT_SECRET required Its secret. Used for the browser sign-in flow only.
APPLE_BUNDLE_IDS for Apple apps The bundle identifiers whose Sign in with Apple tokens this server accepts, comma-separated. Left out, it says so at startup and the iPhone, Mac and Watch apps cannot sign in. There is no client id and no secret — the audience of a native Apple token is the bundle id itself.
PUBLIC_ORIGIN recommended The address this server is served from. Defaults to http://localhost:8080. Share links are built from it, and state-changing requests that say they came from elsewhere are refused.
REDIRECT_URI optional Where Google sends the browser back to. Defaults to http://localhost:8080/auth/callback; set it to match your own address.
BASE_PATHoptional Where this server is mounted under its host, such as /sl, when a domain has several things behind it. Empty by default, meaning the root. The proxy in front must pass the prefix through rather than strip it — in Caddy that is handle and not handle_path — because the server also writes the prefix into every link it emits, so it is the half that has to know. Give the apps the whole address, https://example.com/sl.
BINDoptional The interface to listen on, as an address and never a name. Defaults to 0.0.0.0 — every interface, which is what a phone on the same Wi-Fi needs. Set it to 127.0.0.1 behind a reverse proxy on the same machine, so the proxy is the only thing on a public port and nothing else on the network can skip it. The server says so at startup when it is bound this way.
PORT optional Defaults to 8080, under TLS as well. A process that cannot bind 443 without help should not be told to try by a default.
SESSION_INSECURE optional Set to true only for a local run over plain http://. Anything reachable from outside must not have it — the session cookie is marked Secure unless this says otherwise.
GOOGLE_IOS_CLIENT_ID optional Only for an iOS build that still signs in with Google. The shipped Apple apps do not — they use APPLE_BUNDLE_IDS.
GOOGLE_ANDROID_CLIENT_ID optional Normally nothing. Android is given the web client id above and its tokens come back addressed to that. Set this only if one turns up addressed elsewhere.

The certificate

Name Needed What it is
TLS_MODE optional off (the default), files or acme.
TLS_CERT
TLS_KEY		 with files PEM paths. The full chain, not only the leaf.
TLS_DOMAINS with acme The names to certify, comma-separated. An IP address is refused here rather than minutes later by the CA, which no public authority will certify.
ACME_CONTACT optional An address for expiry warnings. A bare address is read as mailto:.
TLS_CACHE_DIR optional Where the certificate and account key live. Defaults to ./tls, is created 0700, and an existing directory that is more open than that is refused rather than quietly narrowed.
ACME_DIRECTORY optional staging to use Let’s Encrypt’s staging CA while testing. Production otherwise — deliberately, since a staging certificate fails in a way that looks like success.
HTTP_REDIRECT_PORT optional A plain-HTTP listener that serves no application and only redirects to HTTPS. Defaults to 80 when TLS is on, to nothing when it is off, and off turns it off.

Logs and metrics

Name Needed What it is
LOG_LEVEL optional error, warn, info, debug or trace — or a per-crate filter such as api=debug,domain=trace if you want that instead. See what the log contains before choosing.
LOG_FORMAT optional text (the default) or json, for a log that is going somewhere that will parse it.
RUST_LOG optional The same idea, for anybody who already thinks in these. LOG_LEVEL wins where both are set, and the server says so at startup rather than letting a variable left over in a shell quietly beat the one you meant.

METRICS_BIND

METRICS_OTLP_INTERVAL_SECONDS optional How often to push. Defaults to 60.

Running it as a service

Everything above starts the server in a terminal, which is the right way to watch it work once. To have it survive a reboot and a crash, hand it to systemd. The unit is ops/shopping-list.service in the source, alongside a matching section in ops/README.md.

Three locations, kept apart deliberately:

PathOwnerWhat lives there
/usr/local/bin/root The binary. Not writable by the account that runs it.
/etc/shopping-list/server.envroot, 0600 The settings, including the Google client secret.
/var/lib/shopping-list/the service user The database, and the certificate cache if this process holds one.

The database has to live under /var/lib. The unit sets ProtectSystem=strict, which makes the whole filesystem read-only to this service apart from what StateDirectory= grants it. A DATABASE_URL pointing anywhere else — /usr/local/share, /opt, a home directory — fails with (code: 14) unable to open database file, which sounds like a permissions problem on the file and is really a read-only mount.

The account comes first

systemd will not create the user named in User=. A missing one fails the unit before the binary runs, so the journal holds Failed to determine user credentials: No such process and not one word from the server — which never started. That message names neither the user nor the fact that it is absent.

sudo cp ops/shopping-list.sysusers /usr/lib/sysusers.d/shopping-list.conf
sudo systemd-sysusers

# or the same thing by hand
sudo useradd --system --no-create-home --shell /usr/sbin/nologin shopping-list

Then the binary, the settings and the database

sudo install -o root -g root -m 0755 shopping-list-server /usr/local/bin/
sudo install -d -o root -g root -m 0755 /etc/shopping-list
sudo install -o root -g root -m 0600 /dev/null /etc/shopping-list/server.env
sudoedit /etc/shopping-list/server.env

# The server opens the database but will not create it, so that a wrong
# path fails loudly instead of quietly serving an empty list. An empty file
# is enough -- the migrations fill it on the first start.
sudo install -d -o shopping-list -g shopping-list -m 0700 /var/lib/shopping-list
sudo install -o shopping-list -g shopping-list -m 0600 /dev/null /var/lib/shopping-list/data.db

sudo cp ops/shopping-list.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now shopping-list

With DATABASE_URL="sqlite:///var/lib/shopping-list/data.db" in the settings file. Mind the three slashes: two belong to the URL scheme and the third is the root of an absolute path.

The settings are read by systemd, not by the server

The unit uses EnvironmentFile=, and that is worth understanding rather than copying. systemd loads the file as root, before it drops privileges — so the file holding your Google client secret never has to be readable by the account the server runs as.

A .env beside the binary is the opposite: the server looks for one starting from its working directory, which puts the secret somewhere anything running as that user can read. Under systemd, keep the settings in /etc and let it hand them over.

The syntax is close to a .env but not identical — no export, no # comment part-way along a line, and quote any value containing spaces.

Claiming it

The claim code is printed once at startup, while nobody owns the server:

sudo journalctl -u shopping-list -n 40

It is new on every restart and never stored, so one read out of last month’s journal is worth nothing.

When it will not start

First work out whether the binary ran at all. If the journal holds systemd’s own failure line and nothing from the server, it failed before exec and the server never had a chance to speak.

systemctl status shopping-list -l --no-pager
systemctl show shopping-list -p Result -p ExecMainStatus -p ExecMainCode
StatusServer reached?What it means
217/USERnoThe shopping-list account does not exist.
203/EXECnoThe binary is missing, not executable, or built for another architecture.
200/CHDIRnoWorkingDirectory= does not exist.
226/NAMESPACEnoA sandbox directive cannot be applied on this kernel.
“Failed to load environment files”no/etc/shopping-list/server.env is not there.
1yesThe server ran and refused. Its own reason is the line above in the journal.

Only the last means the server was reached. A wrong architecture is worth ruling out early — file /usr/local/bin/shopping-list-server should say x86-64, and ldd --version should be 2.28 or newer.

To take systemd out of it altogether and hear what the server itself says:

sudo -u shopping-list env $(sudo cat /etc/shopping-list/server.env | grep -v '^#' | xargs) \
    /usr/local/bin/shopping-list-server

That runs without the sandbox, so a path the service cannot write but your shell can will work here and fail under systemd. If it starts by hand and not as a service, suspect ProtectSystem=strict and the note about /var/lib above.

To check the unit parses, which catches a directive written into the wrong section:

systemd-analyze verify /etc/systemd/system/shopping-list.service

Once the server is running it refuses to start rather than serve on settings it cannot make sense of — a TLS_MODE it does not recognise, a METRICS_PORT colliding with the application’s, a scrape endpoint on the network with no token, a database path that is wrong. Each is one line in the journal. The unit gives up after five attempts in two minutes rather than restarting for ever, because a loop buries that line; systemctl reset-failed shopping-list clears the count once it is fixed.

Checking on it

systemctl status shopping-list
journalctl -u shopping-list -f
curl http://localhost:8080/healthz

/healthz answers ok and a line saying what TLS is doing, including the certificate authority’s own words when an order failed. The plain listener serves it too, so it answers even while handshakes are failing.

Connecting an app

Install the app and it opens straight onto a list of its own, with no server. When you have one, put its address in under Settings → Server — something like https://lists.example.com — and sign in. Everything the app was already holding is carried up to the server, keeping its own names for things, so running the move twice cannot make a second copy of your shopping.

Changing to a different server later signs you out and clears the lists held on the device, because those belong to the old one.

Things that catch people out

  • localhost on a phone means the phone. Use the address the server prints at startup, and make sure the phone is on the same network.
  • Released apps refuse plain http://. Every client, not only Android. Development builds keep a cleartext exception for a server on the same desk; a shipped one does not, because the token in every request is a bearer credential and on plain HTTP it travels in the clear.
  • A certificate from your own CA is not trusted just because you installed it. Android has not trusted user-added authorities for app traffic since Android 7 — a CA added through Settings is trusted by the browser and by nothing else. This reads as “the certificate is wrong” when what is wrong is that nobody asked the app to trust it.
  • “This account may not use this server” means sign-in worked and the address is not admitted. Add it under Who may sign in and try again.
  • The watch is set up by the phone. Open the app on the paired iPhone once; the watch takes the address and the sign-in from there. A watch that has never heard from its phone says so rather than asking you to type a URL on your wrist.

When something is wrong

Every app can write a log and hand it to you as a zip, under Settings → Diagnostics. The watch has no screen for this — its log comes out through the paired phone.

There are four levels, and the choice matters:

  • Off still records failures. That is what makes a report useful, and it is the setting to leave it on.
  • Basic adds what happened — which request, how long it took, how big the answer was, how deep the queue is. No names of lists and nothing on them.
  • Detailed and Everything record the contents of your lists. The app asks you to confirm before turning either on, because the log is yours until you send it to somebody — and then it is theirs.

The same rule holds on the server, and it is structural rather than a matter of care: at info and above the log physically cannot carry the contents of anybody’s list. Turning the server up to debug prints a warning saying what that now means.

The apps can also report their own timings to an OpenTelemetry collector you run — Settings → Metrics, and only when a server is configured, because a device answering for itself has nothing to measure and nobody to tell. Nothing about what is on your lists is included, and nothing is sent at all until you fill the field in.
